> **状态**：设计稿（2026-11-05），**待 review 后动工**。
> **目标**：把战斗联机从「Host 权威模拟 + 客户端纯播放」升级为王者荣耀式**乐观帧同步**：Host 只中继输入，各端跑同一套确定性模拟，输入按目标 tick 对齐，运行时 hash 比对。
> **首期范围**：F0 确定性基线 → F1 双端同构（影子模式）→ F2 View 切本地 Sim。预测回滚（F3）/重连观战反作弊（F4）后置。

> **分支**：`feature/frame-sync`（基线=master `9ea7475d`）。

## 0. 结论先行

- **路线 A（双 Runner 同构）**：复用现有 `BattleSimState/TurnResolver`，把 `RTSFlowController` 拆成「tick 驱动 + 输入源」；Host 只广播输入批，各端在同一 `targetTick` 结算。改动集中在装配/输入通道/tick 调度，不动结算核心。
- **不选 B（纯 C# 内核抽取）**：`TurnResolver` 1900+ 行、113 处 `Mathf`、`Unit` 是 MonoBehaviour——首期做等于重写战斗核心，风险不可控。B 作为 F2 之后的独立重构缝。
- **不选 C（影子校验）**：只能验证、不能驱动渲染，走不到预测回滚。
- **首期成败判据**：双端 10 分钟对局，每秒 hash 全一致；回放 harness 仍 PASS；AI 行为无回归。

## 1. 目标与非目标

### 1.1 目标（首期 F0~F2）

1. **各端同构模拟**：客户端也实例化 `BattleSimState` 并跑 `TickAdvance`，不再只是「播放 Host 结果」。
2. **Host 只中继输入**：Host 广播的是 `InputBatch`（玩家/AI 的行动），不是结算后的 `Segment`。
3. **tick 对齐**：所有输入带 `targetTick`，各端在同一个 tick 应用同一批输入，结算结果一致。
4. **运行时 hash 校验**：各端每秒计算状态 hash，客户端上报，Host 汇总比对；失配可定位到 tick。
5. **View 最终由本地 Sim 驱动**：F1 先影子校验（View 仍用 Host Segment），F2 切本地 Sim 产出的 Segment。

### 1.2 非目标（首期不做）

- 本地输入预测与回滚（F3）
- 断线重连追帧、观战、独立战斗服（F4）
- 反作弊/输入校验硬化（F4）
- 跨平台（Android/iOS）确定性验证（F0 只保证同平台/同架构）

## 3. 目标架构

### 3.1 拓扑

```
Host（权威输入中继 + 模拟）
  ├─ TickDriver（accumulator → TickAdvance）
  ├─ HostInputSource：本地真人输入 + AI 三脑行动
  ├─ InputBatcher：校验 → 定序 (targetTick, playerId, seq) → 广播
  ├─ Sim（BattleSimState/TurnResolver）在 targetTick 结算
  └─ HashAggregator：收客户端 HashReport，比对告警

Client（同构模拟）
  ├─ TickDriver（同一 tick 频率）
  ├─ ClientInputSource：只消费 Host 下发的 InputBatch
  ├─ Sim（同一套 BattleSimState/TurnResolver）
  ├─ HashReporter：每秒上报本地 hash
  └─ View：F1 用 Host Segment；F2 用本地 Sim 产出的 Segment
```

### 3.2 角色差异（唯一允许的分叉）

| 环节 | Host | Client |
|---|---|---|
| 输入来源 | 本地真人 + AI 三脑 | 网络 `InputBatch` |
| AI 节拍 | 跑（生成行动） | **不跑**（只消费 Host 批里的 AI 行动） |
| 输入校验 | 跑（权威） | 不跑（信任 Host 批） |
| hash | 计算 + 汇总比对 | 计算 + 上报 |
| View 源 | 本地 Sim Segment | F1=Host Segment / F2=本地 Sim Segment |

**铁律**：除上表外，任何结算逻辑不得有 `if (isHost)` 分支——同构的前提是「同一份代码、同一批输入、同一个 tick」。

### 3.3 tick 时序

```
tick N-1        tick N                  tick N+1
  │               │                       │
  ├─ 应用 InputBatch(N)（若有）
  ├─ 移动推进 RTSMovementSystem.AdvanceTick
  ├─ Host: AI 节拍（%10）→ 生成行动 → 塞入 targetTick=N+1 的批
  ├─ 秒拍（%20）：发放/Buff 计时/采集/建筑/快照/hash
  ├─ 胜负检查
  └─ 产出 Segment（View 消费）
```

- **输入批必须在 `targetTick` 之前到达**；Host 至少提前 1 tick 广播。
- **迟到输入**：Host 若发现 `targetTick <= 当前 tick`，重定基到 `当前 tick + 1`；超过 `MaxInputLatenessTicks=10` 丢弃并回执。
- **AI 行动**：`targetTick = 当前 tick + 1`（不需要人类输入延迟），随下一批广播。

## 4. 输入管线与协议

### 4.1 消息类型（新增）

| 类型 | 方向 | 载荷 |
|---|---|---|
| `InputCommand` | Client→Host | `playerId, seq, submitTick, action(ActionData)` |
| `InputBatch` | Host→All | `tick, List<OrderedInput>`（Host 定序后的整批） |
| `HashReport` | Client→Host | `tick, hash, unitCount` |
| `DesyncAlert` | Host→Client | `tick, hostHash, clientHash`（诊断用，F1 只日志） |

### 4.2 定序规则

- 排序键：`(targetTick, playerId 升序, seq 升序)`。
- Host 是唯一定序者；客户端不重排，按批内顺序结算。
- 同一 tick 内多个行动的执行顺序=批内顺序（与现有「枚举序铁律」一致）。
- `seq` 由客户端单调递增；Host 只用于同玩家去重/诊断，不参与跨玩家排序。

### 4.3 输入延迟

- 默认 `InputDelayTicks = 4`（200ms），LAN 可下调到 2；常量收口 `BattleMetrics`。
- 客户端在本地 tick T 提交 → `targetTick = T + InputDelayTicks`。
- Host 若本地 tick 已超过 `targetTick`，按 §3.3 重定基。
- F3 预测回滚后，本地输入可立即表现，权威批到达后校正；F1/F2 不做。

### 4.4 与现有 `ActionData` 的关系

- 复用现有 `ActionData`（`turnNumber/submitTick/aimX/aimZ/targetX/targetZ/...`）。
- `InputBatch` 额外携带 `tick`；`ActionData.turnNumber` 在结算时由 `targetTick` 覆盖，避免旧字段语义漂移。

## 5. 模拟推进改造

### 5.1 `RTSFlowController` 拆分

| 现状 | 目标 |
|---|---|
| `OnSubmitAction` 直接结算 | 改为 `EnqueueLocalInput`（Host）/ `ReceiveInputBatch`（Client） |
| `RunAiBeat` 无条件跑 | 加 `if (!IsHost) return;` |
| `TickAdvance` 内移动/AI/秒拍 | 加「应用 InputBatch」为第一步 |
| `ComputeStateHash` 每秒 | 保留；Host 额外汇总客户端上报 |

新增字段/方法：
- `bool IsHost`
- `Queue<InputBatch> _pendingBatches`（按 tick 排序）
- `ApplyInputBatch(int tick)`
- `BroadcastInputBatch(...)`（Host）
- `ReportHash(...)`（Client）/ `OnHashReport(...)`（Host）

### 5.2 客户端装配

新增 `BattleSession.CreateClientSim(...)`：
- 创建 `BattleSimState`（同 seed、同地图）+ `RTSFlowController`（`IsHost=false`）
- 创建 `BattlePlayer`（View）
- 注册下行路由：`BattleStart`（建盘 + 建 Sim 单位）、`InputBatch`、`Snapshot`（仅诊断/自愈）、`BattleOver`
- 上行路由：`InputCommand`、`HashReport`

**关键难点：客户端 Sim 需要 `Unit` 实例图**。现状 `Unit` 是 MonoBehaviour（组件容器：`UnitIdentity/UnitMoveable/UnitGridPosition/...`），由 `UnitFactory` 在 Host 场景实例化。首期方案：
- 客户端在 `logicRoot` 下用同一 `UnitFactory` 实例化「逻辑 Unit」（不建 `UnitView` 立牌），与 View 层分离；
- 后续 B 路线再把 `Unit` 抽成纯数据类（不在首期）。

### 5.3 开局同步

- `BattleStartMessage` 增加 `seed`、`roster`、`map`（已含 map）、`initialSnapshot`（已有）。
- 客户端用同 seed 建 `BattleSimState`，用 `initialSnapshot` 建单位初始态；**不重放开局命令**。
- Host 在 `StartBattle` 后广播 `InputBatch` 从 tick 0 开始。

## 6. 确定性纪律

### 6.1 硬规则（新增代码必须遵守）

1. **模拟层禁止**：`UnityEngine.Random`、`Time.*`、`DateTime.Now`、`Guid.NewGuid`、`GetHashCode()` 排序、`Dictionary` 直接遍历结算。
2. **随机**：只用 `BattleSimState.RollChance`（`System.Random(seed)` 单出口）；客户端不得新增随机调用。
3. **遍历**：所有影响结算的集合遍历必须显式排序（`unitId` 升序；同 id 用 `seq`/`buffKey` 等稳定键）。
4. **浮点**：新增结算逻辑优先整数/定点；必须用浮点时，只用 `+ - * /` 与 `Mathf.RoundToInt/FloorToInt/CeilToInt/Max/Min/Clamp`，**禁止** `Sqrt/Sin/Cos/Atan2/Pow` 进入「结果分叉」路径（比较/取整前先转整数）。
5. **平台**：F0 只保证同平台同架构；跨平台验证列入 F4。

### 6.2 F0 审计与整改清单

| 项 | 数量 | 整改 |
|---|---|---|
| `Mathf.Sqrt` | 7 | 逐点检查：距离比较改平方比较；必须开方的用整数 `SqrtI`（`RTSMovementSystem`/`SkillHitResolver` 已有） |
| `Mathf.RoundToInt/FloorToInt/CeilToInt` | 55 | 确认输入域为整数/定点；保留（确定性 OK） |
| `Mathf.Max/Min/Clamp` | 51 | 保留（确定性 OK） |
| 字典遍历 | 47 | 逐点加「排序后遍历」；优先改 `sim.Units` 的结算消费点 |
| 排序 | 30 | 检查比较器是否全序 + tie-break（`unitId` 升序） |
| 浮点字段 | 11（TurnResolver/DamagePipeline） | 评估是否进入 hash/结算分叉；必要时定点化 |

**F0 验收**：`ReplayRunner` 双跑同 seed 同命令，hash 序列逐 tick 一致；新增「同输入双跑」自动化断言。

## 7. hash 与失配处理

### 7.1 hash 覆盖范围（需补齐审计）

现有 `ComputeStateHash` 覆盖战场状态；F1 前逐项确认必须包含：

- 单位：`unitId, posX/posZ(cm), hp, energy, sanity, buffs(key/level/remaining), cooldowns, equipment, dimension, isCorpse, DeployedTurn, LastPeriodicSummonSecond`
- 玩家：`mora, stamina, handCards(排序后), 已解锁/已购买`
- 战场：地形变更、资源点余量、建筑周期计数
- 模拟：`CurrentTick, RNG 内部状态`（`System.Random` 无法直接导出状态——**改用自研可序列化 RNG**，见 §7.3）

### 7.2 频率与上报

- 每秒（20 tick）计算一次，随 `HashReport` 上报；Host 汇总。
- 失配：`GICLog.Error("[Desync] tick=… host=… client=…")` + 落盘 `DesyncReport`（tick、双方 hash、单位快照摘要）。
- F1 只告警不中断；F2 后可选「Host 下发快照重同步」（F4）。

### 7.3 RNG 状态可序列化（F0 必做）

`System.Random` 内部状态不可导出，跨端无法在 hash 中比对，也无法在重连时恢复。F0 替换为自研 `DeterministicRng`（xorshift/PCG，`uint state` 可序列化），接口保持 `NextDouble()/Next(int)`；`BattleSimState` 单出口不变。

## 8. View 策略

### 8.1 F1：影子模式

- 客户端 Sim 正常推进、算 hash；**View 仍消费 Host 的 `Segment`**（现有链路零改动）。
- 目的：先证明「双端同 tick 同结果」，不引入表现层风险。
- 验收：10 分钟对局 hash 全一致；画面与 Host 无可见差异。

### 8.2 F2：本地 Sim 驱动

- 客户端 `TurnResolver` 产出的 `Segment` 直接喂 `BattlePlayer.OnSegment`；网络 `Segment` 降级为诊断/回退。
- 目的：为 F3 预测回滚铺路（本地模拟必须能驱动表现）。
- 验收：双端画面一致；断 Host 下行后，已确认 tick 仍能播完。
